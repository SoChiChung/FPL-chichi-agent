## 第二次失败：detached HEAD 导致 git push 报 128

- 用户推送后手动跑 workflow（run 33857888754），闸门+大脑两个 step 已成功（说明 python3 修复生效），但第 5 步「自动提交数据更新」又 exit 128 失败。
- 根因：`actions/checkout` 默认 `fetch-depth: 1` + checkout 触发 commit 的 SHA，处于 **detached HEAD**。step 里裸 `git push` 找不到当前分支映射 → fatal 128。这是 schedule/workflow_dispatch 定时任务 push 的经典坑。
- 修复（提交 `ad9a4ff`）：①顶层加 `permissions: contents: write`；②checkout 加 `fetch-depth: 0`；③`git push` → `git push origin HEAD:main`。
- 排查手段：匿名 API 能拿 job 列表/annotation（只有笼统 `exit code 128`），但**下载日志需 admin 权限（403）**；用 WebSearch 确认 detached HEAD 是 actions/checkout 默认行为。

## 第三次排查：17:34 手动成功后 2 小时无自动 update

- 现象：17:34 手动 workflow_dispatch 成功后，到 19:45 无一次自动 schedule 触发。
- 证据：①runs API 显示 17:34 那次 `workflow_dispatch` **success**（bot 已把 state.json 的 last_update 更新为 `09:34:52Z` 并 push，说明 detached HEAD 修复验证生效）；②17:34 后无任何 schedule run；③模拟当前时刻跑 `decide()` 得 `due=True reason=hourly`（age=130min，ttl=345min），闸门本该放行。
- 根因：**GitHub schedule 是"尽力而为"**，官方文档明示高负载时延迟/丢弃。`*/10` 设定 144 次/天，实际触发只有**每天 3-4 次**、间隔 2-10 小时随机（runs 历史从 08-30 至今一直如此）。cron 不等于准点计时器。
- 结论：不是代码 bug，是 GitHub schedule 的固有限制，无法满足"赛前每小时/每10分钟"刷新。解决需外部调度器（cron-job.org / Cloud Scheduler 调 workflow_dispatch）或接受稀疏节奏。
